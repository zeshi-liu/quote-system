## 1. 销售员 PC 端（已确认）

- 销售员是主要使用者，销售端同步支持 PC Web 和微信小程序。
- PC Web 作为电脑浏览器中的销售工作台，无需安装独立桌面客户端。
- 两端使用同一业务账号、订单、报价、回款数据及权限规则，避免重复录入。
- PC 使用账号密码登录，小程序微信身份绑定同一内部账号；账号由管理员预先创建。密码初始化、重置及首次绑定验证的具体流程在详细设计中确定。
- 医院端继续使用轻量小程序，厂家继续通过本次询价 H5 填写报价。
- MVP 暂不做销售主管角色、主管入口及团队汇总；销售员和内部管理员角色分别保留，订单业务由负责销售员处理。
- 内部管理员仅使用 PC 管理端，账号密码登录，无管理员小程序入口；可维护账号、医院、采购员、厂家、商品及模板，只读查看全量业务订单、报价、回款和图表。
- 管理员不代销售执行报价、账期、回款、异常处理或历史补录核实等业务操作；维护医院基础资料不包含账期字段授权，变更医院负责人及停用账号不自动改写旧单。
- 业务只读之外增加明确例外：销售离职时，管理员可专项交接未完成业务、未结清应收及待处理事项后停用账号，保留原负责人和全部历史操作。交接仅改变后续处理责任，不改金额、账期、报价快照或异常暂停状态。

建议的场景分工：PC 侧重点支持表格录入、厂家比价、批量计价、导出、历史订单查询、回款台账和数据分析；小程序侧重点支持拍照录入、外出查询、业务跟进及回款提醒。具体页面和操作范围在页面设计时细化。

## 2. 报价业务规则（已确认）

| 事项 | 决策 |
| --- | --- |
| 双厂家均无法供货的行 | 保留原采购行，在报价单中明确标记缺货，其余可供货行继续报价。 |
| 一家缺货、另一家尚未提交 | 暂不允许发送其余行报价，等待另一家提交后再决定；尚未提交不能当作缺货。 |
| 整单均缺货 | 两家均明确缺货时，也允许生成并发送全缺货报价单。 |
| 全缺货流程结束 | 医院确认已知悉缺货后，由销售员标记完成。 |
| 规格和单位 | 厂家必须严格按采购行的规格和单位报价，不能自行更改。 |
| MVP 单位 | 仅使用 kg。 |
| 厂家报价有效期 | 厂家填写报价有效至日期；到期后必须重新询价。报价有效期与 H5 链接的 48 小时填写期限分开。 |
| 厂家链接再次发送（2026-10-16 确认） | 页面关闭或原文丢失后重新生成新链接，二次确认并提示旧链接及其 H5 会话立即失效；原 token 仍只存哈希、不恢复。未提交时只更换填写入口，已提交后沿用重新询价、旧提交退出计算和关联报价失效规则，不能借重发静默撤回报价。 |
| 后到厂家报价 | 先提示差异，销售主动刷新后才采用，不自动更新草稿已采用的基准和推荐价，不覆盖最终价；已导出版本不变。基准变化后保留最终价格值，重新确认相关行及风险。 |
| 冻结报价所选基准失效 | 所选基准报价被重询、取消或替换后，相关未完成医院报价保留历史，禁止失效后的再发送和新确认，须出新版本；失效前已实际确认的仍可在满足原有效期、有效发送及当前采购版本等条件时补录。记录首次失效时间与原因，不因厂家新提交而恢复旧版本。 |
| 医院报价有效期 | 默认取所有有价格行所选基准厂家报价中最早的到期日；销售可缩短、不可延长。全缺货单不设价格有效期。 |
| 旧采购版本确认 | 采购明细产生新版本并重新询价后，旧采购版本对应的报价保留历史，不再接受为当前订单的最终确认。 |
| 采购修订不回退（2026-10-16 确认） | MVP 不单独作废新修订后恢复旧修订；误建时当前草稿直接改正，已经冻结则创建下一修订，即使尚未生成链接也不直接解冻覆盖。旧链接和旧报价保持历史资格，不重新恢复；整单确实终止时另走整单作废。 |
| 最终确认后其他未发送版本 | 同一采购版本下确认某个已发送报价后，其余未发送版本全部作废，包括草稿及已导出未发送版本，不论版本号早晚；保留文件与历史，禁止以后再发送。其他已发送历史仅只读，不能产生第二个最终确认或重复应收。 |
| 医院最近 3 次历史价 | 每张采购单占一条，优先取已确认报价，否则取最近已发送报价版本。 |
| 过期后补录医院确认 | 认可有效期内实际发生的医院确认，同时记录实际确认时间、系统补录时间和补录原因。 |

## 3. 医院归属交接（已确认）

- 医院从销售 A 转交销售 B 后，仅新订单归 B，旧订单仍由 A 处理。
- 历史操作人的署名始终保留。
- B 可以只读查看该医院的旧订单、历史报价和医院整体统计；旧订单仍由 A 处理，B 不能修改旧单、代为确认或登记旧单回款。
- 旧单回款提醒仍归 A，B 的读取授权不改变旧单负责人及历史署名；管理员全量业务只读、不代操作，MVP 不做销售主管角色。
- 上述为普通医院交接；离职专项交接明确移交的旧单，后续操作和提醒转给接手销售，历史署名不变。停用原账号前需核对待处理事项和医院新单负责人，不能让业务无人接手。

## 4. 历史订单与回款（已确认）

### 4.1 真实业务需求

销售员需要查找医院历史订单，解决纸质订单过多、遗失、找不到的问题；需要知道每笔订单何时到期、应收多少、已收多少、还差多少。

历史订单档案与“最近 3 次历史报价”是不同功能，不能用最近 3 次报价代替完整订单查询。

历史纸单允许通过专用入口补录实际接收日期、医院最终确认金额及已有回款，无需重新跑厂家询价流程。必须补齐药品及数量并经销售核实后，才能纳入回款台账与统计；缺明细、未核实资料只暂存，不参与正式指标。

专用历史补录仅内部可见，按业务权限供销售和 PC 管理员查阅，管理员仍只读。医院端在草稿、待核实、已核实阶段均不展示；即使属于同医院或关联采购员本人，也不得通过列表、详情或附件读取补录、核实及回款资料。正常医院提交及销售为采购员代录的新单继续按既有权限展示。

历史已有回款缺少逐笔支付日期时，允许登记经核实的“历史累计已收”，后续新回款逐笔记录。历史累计明确标识，不伪造支付日期，不与其包含的逐笔款重复累计，误录时仍按作废重录保留痕迹。

已核实历史纸单的最终确认金额录错时，允许当前订单负责销售员通过专用入口更正，原因必填，原核实金额及每次更正前后值、操作者和时间均保留；新应收不得低于有效已收，包含有效历史累计与后续逐笔回款。更正同步历史当前金额、已有应收、余额、结清、提醒及原业务期间的金额统计，不新增订单或应收，不改真实回款、数量、账期和实际日期，不自动解除异常暂停；普通新单改价或实际取消/退款不得使用此入口。

历史补录核实及每次金额更正均须填写核实依据和说明，附件可选；原纸单遗失也可按其他已确认校验办理。服务端拒绝缺失或仅空白的依据/说明，有附件也不能省略文字记录；补录草稿可先暂存，核实生效前其他明细、日期、原账期、金额等必填条件仍须满足。首次核实及各次更正的依据和说明分别留存。

历史单的药品、采购需求数量、原账期、最终金额和其他必填资料已核实时，逐行确认数量或缺货状态未知仍可入账；该单次数、需求及已核实金额照常纳入。确认/缺货指标只汇总有依据的数据，未知留空并提示覆盖；没有已知值时显示未知，部分已知标为已知部分合计，不能以 0、全部供货或需求减已知确认量的差额代替。

### 4.2 回款规则

| 事项 | 决策 |
| --- | --- |
| 账期起点 | 从医院采购单发来、实际接收的日期起算，而非系统录入日期。 |
| 账期天数及权限 | 默认 90 天，按医院分别配置，由具备医院权限的销售员维护；医院端不能操作账期页面或修改账期。此规则取代此前“统一一个账期天数”的初步选择。 |
| 默认账期变更 | 普通新单创建时保存当时账期；销售修改医院默认账期只影响之后新建订单，旧订单账期和到期日不自动改变。 |
| 订单账期单独调整 | 该订单负责销售员可以单独调整，必填原因并保留前后账期、到期日及操作人和时间；只影响本单，不改医院默认值和应收、回款金额，提醒按新到期日计算。 |
| 历史订单原账期 | 由销售按当时约定填写；未知时保留待核实，不用默认 90 天或医院当前账期代替，不推定到期日及逾期。 |
| 应收金额 | 以医院确认的最终报价金额为准。 |
| 回款方式 | 按订单记录回款，同一订单可能分多次支付。 |
| 回款误录更正 | 该订单负责销售员可作废错误记录，必填原因、保留原记录，再录入正确金额；不直接修改或删除原记录。作废记录不计入累计已收，重新计算余额及提醒，作废误录不表示实际退款。 |
| 历史核实金额录错 | 当前订单负责销售员必填原因、保留原核实金额和历次前后值后专用更正，新应收不得低于有效已收；同步台账、余额及统计，不能用于实际取消/退款或正常新单改价。 |
| 超额登记 | 回款金额超过订单当前未收余额时阻止录入，提示核对金额或订单；并发和重试也不得导致累计超收，不产生负数未收余额。 |
| 取消/退款请求 | 已形成应收时先标记“取消/退款待处理”、暂停该单自动催收，保留全部金额及历史，由销售线下核实；不自动冲销应收或执行退款。异常订单仍在台账可查，不等于结清或已退款，账期或回款变化不自动解除异常。 |
| 异常解除 | 线下核实仍需正常收款时，原订单负责销售员可填写核实结果和原因、留痕解除；按当前到期日及未收余额恢复正常催收，原异常历史保留，不改金额，也不表示结清或已退款。 |
| 提醒渠道 | 小程序内有待回款列表，同时希望在微信中收到通知。 |
| 提醒节奏 | 到期当天开始提醒，逾期后每天提醒。 |

微信通知的实现约束：需结合实际小程序类目、可用模板及用户订阅授权验证。一次性订阅通常只能发送一条消息，不能承诺一次授权后每天持续通知；站内待回款列表须独立可用。参考：[腾讯云：实现小程序订阅消息推送](https://cloud.tencent.com/document/product/1301/103770)。

### 4.3 建议的业务闭环（待纳入详细设计）

- 普通订单保留创建时账期，历史补录保留核实的当时约定；原负责人可留痕单独调整，当前生效账期优先取本单调整值，建立应收不重新读取医院当前默认值。历史原账期未知仍待核实，不能以单独调整绕过核实门槛。
- 一张订单只建立一笔应收；正常单关联最终确认报价，历史补录单关联经核实的历史最终确认金额，重复核实、导出或报价换版不重复生成应收。
- 缺货行不产生应收金额；全缺货订单不产生待回款提醒。
- 未收金额 = 应收金额 − 有效回款记录累计金额；分次回款更新余额，全部收齐后停止提醒。
- 报价流程完成与回款结清分别记录，避免订单标记完成后漏掉回款。
- 旧订单提醒跟随原订单负责销售员，遵循“旧订单仍由 A 处理”。
- 历史纸单支持专用补录，补齐药品数量并核实后纳入；金额尚无依据时保留待核实，不自动推算应收或伪造厂家提交。
- 回款误录更正采用作废重录，超额登记阻止录入，取消/退款先标异常暂停催收；核实仍需正常收款时原负责人可留痕解除。每日 09:00 催收已在第四部分确认；确需取消/退款时的后续金额处理仍待细化，MVP 不自动冲销或执行退款。

历史档案建议支持医院、日期、单号、药品检索，并关联已有采购原图或文件、报价与回款资料；专用补录采购明细须补齐，核实依据和说明必填、附件可选，逐行确认/缺货未知不阻止入账，字段表单布局仍待设计。

## 5. 医院数据分析页面（新增需求）

### 5.1 已确认

- 新增数据分析界面，以图表展示不同医院的要货频率、数量等情况，便于销售员了解医院需求。
- **采购需求与最终确认结果分别展示**，不混成一个指标。
- 采购需求反映医院提出了多少需求，包含最终缺货部分；最终确认结果反映医院确认报价中可供货的数量和金额，缺货情况单独表达。
- 数量使用 MVP 统一单位 kg；最终确认结果不能标为实际发货量或实际销售量。
- 同批需求与最终确认结果按采购单实际接收日期选同一批订单对比；另提供按实际医院确认日期的确认趋势，跨月或补录不混用系统日期。
- 同一采购单只计一次，采购明细修订、厂家重询及报价换版不新增要货次数。正常单需求量使用最新已校对冻结版本；新草稿冻结前沿用上一冻结版本，不能因上一版本已被标为 superseded 而归零。
- 新修订冻结后更新原实际接收期间的需求量、药品排名及相关图表，不把需求移到修订月份；最终确认结果仍取最终确认快照。尚无冻结版本的正常单不把 OCR/草稿数量纳入正式需求量；历史补录仍须完整核实。
- 要货次数与需求量均排除从未冻结的正常单及整单已作废记录；有上一冻结版本的新修订草稿沿用该版本，不因当前重新校对而被排除。全缺货完成单仍计一次要货并保留全部需求，确认可供货量为 0、不产生应收；历史补录仅完整核实生效后纳入，整单作废则排除。
- 整单作废后更新原接收期间的需求图表及下钻，档案与作废历史保留，不自动改账；报价版本作废、厂家任务取消及取消/退款待处理异常均不等于整单作废，不能据此整体排除有效采购需求。
- 历史单逐行确认/缺货未知不排除已核实需求及金额；相关指标仅汇总已知数据，标明未知行及覆盖范围，全部未知留空、部分已知标为已知部分合计，不按需求差额推定缺货。
- 首版五类图表全部纳入：医院要货次数、需求与确认数量对比、周/月趋势、药品数量排名、缺货情况。
- PC 与小程序均提供全部五类图表，统计口径和权限规则一致，小程序适配手机屏幕。

### 5.3 统计规则建议（待确认）

1. 待询价、厂家待提交或待医院确认不能直接算作缺货。可选平均要货间隔仍待细化，周一/月初分组边界已在第四部分确认；采购需求明细不齐或未核实历史补录不纳入正式统计，已核实但逐行确认结果未知不等同于未核实。要货次数/需求量排除及修订回算规则已确认；MVP 不提供单独作废新修订并回退旧版的入口，不另设回退统计口径。
